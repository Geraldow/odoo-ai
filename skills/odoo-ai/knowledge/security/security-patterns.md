# Secure Odoo Coding Patterns

## Purpose

Use these patterns when implementing models, controllers, portals, and admin
features in Odoo custom modules.

## Minimal sudo() Scope

Use `sudo()` only after the user-facing access rule has been checked.

```python
order = self.env["sale.order"].browse(order_id)
order.check_access("read")

# Only this internal write needs elevated rights.
order.sudo().message_post(body=_("Reviewed by operations."))
```

Avoid `self.env["model"].sudo()` at the beginning of a method unless the whole
method is a controlled admin operation.

## Group Checks

Use groups for sensitive operations that are not sufficiently protected by ACLs
or record rules.

```python
if not self.env.user.has_group("base.group_system"):
    raise AccessError(_("Only administrators can perform this action."))
```

Use module-specific groups for business roles instead of relying only on
`base.group_system`.

## Field-Level Access

Protect sensitive fields with `groups=` when the value should not be visible to
all internal users.

```python
secret_token = fields.Char(groups="base.group_system", copy=False)
```

Do not expose sensitive fields in tree/search views, exports, or portal payloads.

## Portal Isolation

Portal flows must filter by the current user's partner or by a valid access
token generated by Odoo. Never rely only on a URL ID.

Safe defaults:
- Use portal helper methods where available.
- Verify `record.partner_id` or commercial partner ownership.
- Use access tokens for shared portal documents.
- Return 404/AccessError when ownership is not proven.

## with_user() vs sudo()

Use `with_user(user)` to evaluate access as another user. Use `sudo()` only to
bypass access intentionally.

| Pattern | Use When | Security Effect |
|---|---|---|
| `with_user(user)` | Simulate or enforce another user's permissions | Keeps ACL/rules for that user |
| `sudo()` | System operation after business validation | Bypasses ACL/rules |
| `with_company(company)` | Multi-company sequence, property, or rule context | Keeps user identity |

## Controller Input Validation

Controllers must convert raw request values into validated domain values.

```python
allowed_fields = {"phone", "mobile"}
payload = request.httprequest.form
vals = {
    key: payload.get(key)
    for key in allowed_fields
    if payload.get(key)
}
```

Checklist:
- Whitelist accepted keys.
- Convert types server-side.
- Validate record ownership before write.
- Use explicit `auth`.
- Keep CSRF enabled for state-changing HTTP forms unless there is a documented
  integration reason.
